# Lab Log writing guidelines

This repository is a personal lab log for the author and readers who may repeat the work. Preserve the feel of a practical forum build thread.

## Organization

- Keep the root README brief, with entry number, linked title, and a short description. Order entries by number descending.
- Use permanent sequential entry numbers: `001`, `002`, and so on. Never renumber existing entries.
- Store each investigation in `entries/NNN-short-name/README.md`, with its own `images/` and `files/` as needed.
- Update the same entry when an investigation spans several days. Record start and update dates; use dated sections only when they help the story.
- Give a substantial subproblem its own entry only when it is useful independently. Link it from the parent investigation and link back.
- Use relative links so entries and images work on GitHub and in a local checkout. Embed images beside the relevant step with descriptive alt text and captions.

## Equipment reference

- Read `equipment/README.md` before asking what equipment is on hand or proposing new purchases. Follow links to relevant characterization records when selecting a test setup.
- Use recorded ownership as the planning baseline. Ask only for missing task-relevant details or current access when an experiment depends on it; do not ask the user to repeat the full inventory.
- Distinguish recorded ownership, recent documented use, shared access, ordered items, and unconfirmed availability. An old order is not evidence of arrival; an update date is not a new physical inventory check.
- Keep source-listed ratings separate from measured results. Respect frequency coverage, sample spacing, calibration context and unresolved inconsistencies. Missing or zero-filled parameters are not measured performance.
- Maintain the equipment reference as a living page outside the numbered entry sequence. When the user confirms a model, purchase, disposal, failure or availability change, update the relevant item and date/source. Preserve original measurement assets and historical entry settings.

## Writing and evidence

- Explain the question, setup, actions, observations, interpretation, and current outcome. Use the template flexibly; omit empty sections.
- Write plainly in the author's voice. First person is welcome for documented actions and preferences. Do not invent thoughts, emotions, or hands-on work.
- AI may organize and draft from supplied notes, conversations, photos, and files. Never fabricate measurements, settings, equipment, dates, quotes, or a successful outcome.
- Distinguish performed steps from proposed next steps. Label estimates, assumptions, and interpretations where they matter.
- Preserve meaningful failed attempts, corrections, and changes of direction. Do not present an earlier interpretation as established after later evidence contradicts it.
- Include enough dimensions, settings, calibration details, and environmental context to interpret or repeat the experiment.
- Check numbers against the underlying files. Separate measured values from derived quantities and explain relevant sampling limits.
- Describe what the results establish and what remains unresolved. A partial success does not make the whole investigation complete.
- Use `In progress`, `Complete`, or `Paused` as a lightweight entry status. Do not mark complete merely because a draft is finished.
- Keep original measurement files unchanged. Put new calculations or summaries in separate files and identify their inputs.
- Use available real photos and captures. Never generate an illustration and present it as experimental evidence.
- Exclude credentials, private host details, and unrelated project material from published assets. Do not assign a license without the author's direction.

## Before finishing

Read the entry from start to finish, verify local links and embedded assets, check quantitative claims, and update the index. Commit and publish only within the user's authorized scope.
